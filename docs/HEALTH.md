## First five commands

```bash
ENV=prod    # or sandbox

# 1. What is not Ready, and why
oc get maasmodelref -A -l maas.pase52.io/environment=$ENV -o jsonpath='
{range .items[?(@.status.phase!="Ready")]}{.metadata.namespace}/{.metadata.name}{"\t"}{.status.phase}{"\t"}{range .status.conditions[*]}{.type}={.status}({.reason}) {end}{"\n"}{end}'

# 2. Governance state
oc get maasauthpolicy,maassubscription -n models-as-a-service -l maas.pase52.io/environment=$ENV

# 3. The workload
oc get llminferenceservice -A -l maas.pase52.io/environment=$ENV
oc get pods -n llm-$ENV

# 4. What the catalogue actually serves
TOKEN=$(oc whoami -t)
MAAS=$(oc get route maas-api-route -n models-as-a-service -o jsonpath='{.spec.host}')
curl -sS -H "Authorization: Bearer $TOKEN" https://$MAAS/v1/models | jq '.data[] | {id, ready, url}'

# 5. What git says should exist
oc get cm -n models-as-a-service -l maas.pase52.io/environment=$ENV -o yaml | yq '.items[].data["models.yaml"]'
```

Command 5 reads the inventory ConfigMap this chart renders. Comparing it against
command 1 answers "is something missing, or was it never deployed?" without
opening git.

## Reading MaaSModelRef

`status.phase` folds two independent questions into one value. The conditions
separate them again:

| Condition | Question |
|---|---|
| `RuntimeReady` | Is the backend up and serving? |
| `GovernanceAttached` | Is there an active `MaaSAuthPolicy` **and** `MaaSSubscription` covering it? |
| `Ready` | Both of the above |

| phase | RuntimeReady | GovernanceAttached | What it means |
|---|---|---|---|
| `Ready` | True | True | Serving |
| `Pending` | False | True | Backend still starting — usually resolves |
| `Pending` | True | False | **Config error.** Model runs; every call is denied |
| `Pending` | False | False | Early in a fresh deploy, or both are broken |
| `Unhealthy` | False | True | **Live outage.** Governed, but the backend is failing |
| `Failed` | — | — | Unrecoverable reconcile error |
| `Invalid` | — | — | Malformed spec |

```bash
oc get maasmodelref <name> -n <ns> -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'
```

## MaaSModelRef not Ready

Alert: `MaaSModelNotReady`. The model has not reached `phase=Ready` within the
grace period.

**1. Split runtime from governance.**

```bash
oc get maasmodelref <name> -n <ns> -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
```

**2a. `GovernanceAttached=False`** — no policy/subscription pair covers the
model. This never resolves on its own.

```bash
# Which policies claim to cover it? The annotation lists them.
oc get maasauthpolicy,maassubscription -n models-as-a-service \
  -o custom-columns='KIND:.kind,NAME:.metadata.name,MODELS:.metadata.annotations.maas\.pase52\.io/managed-models'
```

Both a `MaaSAuthPolicy` **and** a `MaaSSubscription` must name it. One alone is
not enough. If either is missing, the model's `tier` does not match any
`modelSelector` in the environment values file — fix the values, sync.

Note the chart refuses to render this configuration unless
`validation.requireAccessPolicy` / `requireSubscription` were turned off, so on a
chart-managed model this usually means governance objects exist in git but failed
to reconcile. Go to [governance degraded](#governance-degraded).

**2b. `RuntimeReady=False`** — the backend is not serving. Go to
[workload unavailable](#workload-unavailable).

## MaaSModelRef Unhealthy

Alert: `MaaSModelUnhealthy`. Governance is attached but the runtime is failing.
Callers are being refused or timing out **right now**.

```bash
oc get maasmodelref <name> -n <ns> -o jsonpath='{.status.conditions[?(@.type=="RuntimeReady")].message}{"\n"}'

# The route and gateway the controller resolved
oc get maasmodelref <name> -n <ns> -o jsonpath='route={.status.httpRouteName} gateway={.status.httpRouteGatewayName}{"\n"}'

oc get httproute -n <ns>
oc describe llminferenceservice <name> -n <ns> | tail -30
```

Common causes:

| Symptom | Cause | Fix |
|---|---|---|
| HTTPRoute not accepted | `LLMInferenceService` missing the gateway ref | Confirm `spec.router.gateway.refs` names `maas-default-gateway` |
| Pods `CrashLoopBackOff` | Wrong runtime image, or model too large for the node | Check `image` is a vLLM runtime, not a ModelCar; check memory limits |
| Pods `Running`, probes failing | Model still loading past the probe window | Raise `readinessProbe.failureThreshold` |
| Gateway 503 | All replicas unready | `oc get pods -n <ns> -l maas.pase52.io/model=<name>` |

Mitigation while investigating: scale the model to zero so callers fail fast
rather than hanging, or point the tier's `accessPolicy` away from it.

## Governance degraded

Alert: `MaaSGovernanceDegraded`. A `MaaSAuthPolicy` or `MaaSSubscription` failed
to produce healthy Kuadrant policies. Access control or quotas may not be
enforced — treat unenforced quota as a cost incident, not just an availability one.

```bash
oc get maasauthpolicy <name> -n models-as-a-service -o jsonpath='
{range .status.authPolicies[*]}{.name}: ready={.ready} model={.model} {.message}{"\n"}{end}'

oc get maassubscription <name> -n models-as-a-service -o jsonpath='
{range .status.tokenRateLimitStatuses[*]}{.name}: ready={.ready}{"\n"}{end}'

# The controller's own view
oc logs -n models-as-a-service -l app.kubernetes.io/name=maas-controller --tail=100 | grep -i "<name>"
```

| Cause | Fix |
|---|---|
| `modelRefs` names a `MaaSModelRef` that does not exist | Check name **and** namespace; the pair is exact |
| Referenced model is in another namespace than declared | `MaaSModelRef` lives with its backend, not in the tenant namespace |
| Kuadrant/RHCL not healthy | `oc get pods -n kuadrant-system` |
| Invalid rate-limit window | Windows are `s`/`m`/`h` only — `24h`, never `1d` |
| Object in the wrong namespace | Governance objects must be in `models-as-a-service` |

## Workload unavailable

Alert: `MaaSModelWorkloadUnavailable`. A KServe deployment backing a model has
unavailable replicas.

```bash
oc get pods -n <ns> -l maas.pase52.io/model=<name>
oc describe pod -n <ns> <pod> | tail -40
oc logs -n <ns> <pod> -c main --tail=100
```

| Symptom | Cause | Fix |
|---|---|---|
| `ImagePullBackOff` on `registry.redhat.io` | Missing or expired pull secret | Check `global.imagePullSecrets`; verify the secret exists in the model namespace |
| `Pending`, `0/N nodes match` | No GPU capacity | `oc get nodes -l nvidia.com/gpu.present=true`; check `nodeSelector` and `tolerations` |
| `vllm: command not found` | ModelCar image used as the runtime image | `inference.image` must be a vLLM runtime (`rhaiis/vllm-*-rhel9`); the ModelCar goes in `inference.modelUri` |
| `OOMKilled` | Model exceeds the memory limit | Raise limits, lower `--max-model-len`, or use a smaller model |
| Ready but slow first token | Cold start, weights still loading | Expected; raise probe `initialDelaySeconds` if it flaps |
| `CreateContainerConfigError` | Missing credential Secret (external models) | `oc get secret <name> -n <ns>` |
| `Init:Error` / `Init:CrashLoopBackOff` | Model download failed | [S3 download failures](#s3-model-download-failures) |
| `Evicted`, pod restarts mid-startup | Ephemeral storage exhausted by the download | Raise `storageInitializer.resources.requests.ephemeral-storage` above the model size |

## S3 model download failures

Models loaded from `s3://` (or `hf://`) are fetched by an **initContainer**
named `storage-initializer`, so a failure shows as `Init:Error` and the vLLM
container never starts. Its logs are the whole story:

```bash
oc logs -n <ns> <pod> -c storage-initializer
oc get pod -n <ns> <pod> -o jsonpath='{.spec.serviceAccountName}{"\n"}'
```

| Log message | Cause | Fix |
|---|---|---|
| `Unable to locate credentials` / `NoCredentialsError` | The pod's ServiceAccount has no Secret attached | Confirm `serviceAccountName` is set and the SA lists the Secret — see the check below |
| `EndpointConnectionError`, tries `s3.amazonaws.com` | `s3-endpoint` annotation missing from the **Secret** | Settings live on the Secret, not the SA. Set `annotateExistingSecret: true` |
| `SSLCertVerificationError` | Self-signed endpoint (MinIO/ODF lab) | `verifySsl: "0"`, or supply `caBundleConfigMap` |
| `AccessDenied` / `403` | Key lacks `s3:GetObject`/`s3:ListBucket` on the prefix | Fix the bucket policy; verify with `aws s3 ls` using the same key |
| `NoSuchBucket` / downloads 0 files | Wrong prefix, or missing trailing `/` | `modelUri` must point at the directory holding `config.json` |
| `No space left on device` | Ephemeral storage too small | Raise `storageInitializer.resources` above the full model size |
| Very slow, then probe failure | Large model over a slow link | Raise `readinessProbe.initialDelaySeconds` and `failureThreshold` |

Verify the credential chain end to end — all three links must hold:

```bash
NS=llm-prod; SA=maas-s3-models

# 1. The ServiceAccount references a Secret
oc get sa $SA -n $NS -o jsonpath='{.secrets[*].name}{"\n"}'

# 2. That Secret carries the keys KServe expects, under these exact names
oc get secret <secret> -n $NS -o jsonpath='{.data.awsAccessKeyID}' | head -c 8; echo
oc get secret <secret> -n $NS -o jsonpath='{.data.awsSecretAccessKey}' | head -c 8; echo

# 3. ...and the S3 settings, which KServe reads from the SECRET's annotations
oc get secret <secret> -n $NS -o jsonpath='{.metadata.annotations}' | tr ',' '\n' | grep s3-
```

A frequent cause of silent breakage: `annotateExistingSecret: true` without
`ServerSideApply=true` in the Application's `syncOptions`. A client-side apply
prunes the externally-managed credential keys, leaving an annotated Secret with
no data — the initContainer then reports `Unable to locate credentials` on a
Secret that looks correct in the Argo CD UI.

To confirm what the controller actually injected:

```bash
oc get pod -n <ns> <pod> -o jsonpath='{range .spec.initContainers[?(@.name=="storage-initializer")]}{.args}{"\n"}{range .env[*]}{.name}={.value}{"\n"}{end}{end}'
```

## Callers get 401 / 403

Authentication or authorisation, not availability.

```bash
# Is the caller in a group the policy grants?
oc get maasauthpolicy -n models-as-a-service -o yaml | yq '.items[].spec.subjects'
oc get groups | grep -i <group>

# Is the model actually covered?
oc get maasauthpolicy -n models-as-a-service \
  -o custom-columns='NAME:.metadata.name,MODELS:.metadata.annotations.maas\.pase52\.io/managed-models'

# Authorino's view
oc logs -n kuadrant-system -l app=authorino --tail=100
```

`system:authenticated` covers every logged-in user; production policies name
explicit groups instead. A user must be in the group **at token issue time** —
group changes need a fresh token.

## Callers get 429

Quota exhausted. This is the system working, but confirm the limit is the one you
intended:

```bash
oc get maassubscription -n models-as-a-service -o yaml | yq '.items[] | {
  "name": .metadata.name, "priority": .spec.priority,
  "owner": .spec.owner, "limits": .spec.modelRefs}'

oc logs -n kuadrant-system -l app=limitador --tail=100
```

When a caller matches several subscriptions, the highest `priority` wins — not
the most generous. A user in both `maas-users` (priority 10) and `maas-premium`
(priority 20) gets the premium plan. Verify the priorities are ordered as
intended before raising a limit.

## Model missing from /v1/models

`maas-api` lists models from `MaaSModelRef` objects. Absence means the object is
missing, not Ready, or in a tenant the caller cannot see.

```bash
oc get maasmodelref -A | grep <name>
oc get maasmodelref <name> -n <ns> -o jsonpath='phase={.status.phase} endpoint={.status.endpoint}{"\n"}'
```

- No object → the model is `enabled: false` in git, or the sync never ran.
- Object exists, `phase!=Ready` → [not Ready](#maasmodelref-not-ready).
- `Ready` but absent from the API for one user → the caller is not in a group the
  `MaaSAuthPolicy` grants; the catalogue is filtered per caller.

## Argo CD shows Healthy but the model does not work

Almost always: the custom health checks are not installed, so Argo CD treats the
MaaS CRDs as unknown kinds and calls them Healthy on sight.

```bash
oc get argocd openshift-gitops -n openshift-gitops \
  -o jsonpath='{range .spec.resourceHealthChecks[*]}{.group}/{.kind}{"\n"}{end}'
```

Expect five entries: `MaaSModelRef`, `MaaSAuthPolicy`, `MaaSSubscription`,
`ExternalModel`, `LLMInferenceService`. If they are missing, follow
[installation step 1](../README.md#1-install-the-argo-cd-health-checks).

If they are present but health still looks wrong, the Lua may be failing at
runtime — Argo CD falls back to Healthy on a script error:

```bash
oc logs -n openshift-gitops -l app.kubernetes.io/name=openshift-gitops-application-controller \
  --tail=200 | grep -i lua

./tests/lua/run.sh     # reproduce locally
```

## Enabling metrics and alerts

`MaaSModelRef.status.phase` is a custom-resource field. Prometheus cannot see it
until kube-state-metrics is told about it. Without this wiring, only the
`MaaSModelWorkloadUnavailable` alert functions — the phase-based alerts never fire.

**1. Render the CustomResourceState config:**

```yaml
observability:
  customResourceStateMetrics:
    enabled: true
    namespace: openshift-user-workload-monitoring
  prometheusRule:
    enabled: true
```

**2. Mount it into a kube-state-metrics instance** (cluster-admin, once). The
instance needs `--custom-resource-state-config-file` pointing at the mounted
`crs.yaml`, and RBAC to `list`/`watch` `maas.opendatahub.io` resources:

```yaml
rules:
  - apiGroups: ["maas.opendatahub.io"]
    resources: ["maasmodelrefs", "maasauthpolicies", "maassubscriptions", "externalmodels"]
    verbs: ["list", "watch"]
```

**3. Verify the metrics exist:**

```
maas_model_phase{namespace, name, phase}
maas_authpolicy_phase{namespace, name, phase}
maas_subscription_phase{namespace, name, phase}
maas_externalmodel_phase{namespace, name, phase}
```

Useful queries:

```promql
# Models not Ready right now
max by (namespace, name) (maas_model_phase{phase="Ready"}) == 0

# Fraction of the catalogue serving
sum(maas_model_phase{phase="Ready"}) / count(max by (namespace, name) (maas_model_phase{phase="Ready"}))

# Models in a live outage
maas_model_phase{phase="Unhealthy"} == 1
```

User-workload monitoring must be enabled for the `PrometheusRule` to be
evaluated:

```bash
oc -n openshift-monitoring get cm cluster-monitoring-config \
  -o jsonpath='{.data.config\.yaml}' | grep enableUserWorkload
```
